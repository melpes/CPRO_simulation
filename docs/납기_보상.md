# 납기 보상 (W7_DueDate) — 반영 위치 및 메커니즘

## 1. 목적

고객 주문(PO)의 **납기일(DueDay)** 을 강화학습 보상의 생산성 차원에 반영한다. 단순 총생산량(W5)만이 아니라 **"각 모델이 납기 일정에 맞춰 진행되는가"** 를 학습하게 한다.

## 2. 메커니즘 — 페이스 기반 결손 (DuePaceDeficit)

핵심 아이디어: 납기일까지 주문량을 채우려면 일정한 **필요 페이스**가 있고, 그 페이스에 **뒤처진 양(결손)** 을 누적해 페널티로 준다.

**용어**
- `DueDay`: 납기일 (t=0=에피소드 시작 기준 경과일). AAS PO qualifier.
- `Φ(potential)`: 한 상태의 목적함수 값. 보상은 매 결정점 `r_t = Φ(다음)−Φ(현재)` 로 쪼개짐(potential telescoping).
- `_watch` 틱: 30초마다 도는 위반 카운터 누적 루프(W3/W4/W6과 동일 위치).

**모델 m 에 대해 (말 → 식)**
- 필요 진척률 = 납기까지 선형 목표: `r_m = min( now / (DueDay_m × 86400), 1 )`
- 실제 진척률 = `p_m = Throughput_m / target_m`
- 페이스 결손 = 뒤처진 양(앞서면 0): `d_m = max(0, r_m − p_m)`
- 누적(근무 틱마다): `DuePaceDeficit += Σ_m d_m`
- 보상 항: `Φ −= ( DuePaceDeficit / _due_violation_norm ) × W7_DueDate`
- 정규화: `_due_violation_norm = max(1, 모델수 × nominal_work_ticks)` (reset 1회 산출)

**왜 누적(단조 카운터)인가**: potential telescoping은 누적값이라야 중간 위반이 상쇄되지 않는다 — 기존 위반 카운터(W3 재고초과/W4 재고부족/W6 유휴)와 **동일한 패턴**이라 검증된 안전성 위에 얹힌다.

**왜 페이스 기반(타 방식 대비)**
- 지각 페널티: 납기 *후* 에야 발생 → 만기 전 우선순위 학습 불가.
- 납기내 throughput만: 경계에서 이진(1초/10일 늦어도 0) → gradient·선제성 없음.
- **페이스: 매 틱·선제적** — 뒤처진 모델을 만기 전부터 우선하도록 학습. 지각을 자연 포함.

## 3. 반영 위치 (데이터 → 보상)

```
PO(AAS, DueDay)
  └─ path_extractor.PurchaseOrder         (이미 추출: {model: (수량, DueDay, 등록일)})
       └─ run.build_simulation            DueDay = {model: 일×86400} 추출 → env 주입
                                          + RewardWeights 튜플에 'W7_DueDate' 추가
            └─ CproSimEnv (simulation.py)
                 ├─ __init__   : self.DueDay 보유
                 ├─ reset()    : DuePaceDeficit=0, _due_violation_norm 산출
                 ├─ _watch()   : 틱마다 RuntimeVariables.DuePaceDeficit(...) 누적
                 ├─ potential(): − (DuePaceDeficit/norm) × W7_DueDate 항
                 └─ state_vec(): 페이스 결손 채널 +1 (state_dim 18→19, critic 관측)
```

**구현 위치 요약**
- `path_extractor.py` — `RuntimeVariables.DuePaceDeficit(Throughput, target_qty, DueDay, now, DuePaceDeficit)` : 순수 누적 함수(AAS 명시 연산 규약). 진실의 원천.
- `run.py` (build_simulation) — PO에서 DueDay 추출·주입, RewardWeights에 W7 추가.
- `simulation.py` (CproSimEnv) — 주입·reset·_watch 누적·potential 항·state_vec 채널. horizon `EPISODE_DURATION_SEC = 30×86400`.
- `aas_data/ProvisionOfSimulationModel.json` — `RewardWeights`에 `W7_DueDate` Property(value 0.25) + ConceptDescription.

## 4. horizon

`EPISODE_DURATION_SEC = 30일`. 에피소드는 **전 생산 완료 시 즉시 종료**(`_watch`의 `all(Throughput≥target)`)하므로 이 값은 *상한*일 뿐 — 생산이 중간에 잘리지 않게 하는 용도. 더 키워도 무방(완료 시 종료).

## 5. 동작 (검증 결과)

| 설정 | W7 정규화값 | 의미 |
|---|---|---|
| DueDay = 22일 (느슨, 현 baseline) | ≈ 0.02 | 페이스 여유 → 소penalty |
| DueDay = 1일 (빡빡) | ≈ 0.43 | 큰 penalty (발화) |

납기가 빡셀수록 W7이 커진다 — 의도대로 차등 동작.

## 6. 운용 메모

- **현재 PO**: 세 모델 모두 DueDay=22·수량 100 (학습 기준선). 동일 납기에선 W7이 *모델 간 우선순위*를 차별하지 못하고 W5(throughput) 보강에 가깝다.
- **차등 납기**로 바꾸면(예 A=12 / B=22 / C=35) 급한 모델을 먼저 처리하도록 학습된다 — PO 숫자만 조정.
- W5(총 throughput)는 불변. 생산성 차원 = **W5 + W7**.
